# 프로젝트 구조 단기 교육 계획

## 목표와 원칙

- 목표: 현재 구현의 흐름을 이해하고, 기능 수정·추가 시 어느 파일을 고칠지 스스로 판단한다.
- 사용자가 교육 종료를 선언할 때까지 코드 수정 금지. 설명에 필요한 변경도 사용자가 해당 범위를 명시적으로 허용한 경우에만 한다.
- 교육 계획 문서만 갱신하고 기존 코드·설계·진행 문서는 변경하지 않는다. 에이전트는 앱 실행·AWS 호출 없이 소스를 읽으며 설명한다.
- API·라이브러리 세부 사용법, 설계 이론의 심화는 생략한다. 설계 예정과 현재 구현을 구분한다.
- 각 회차는 핵심 설명 → 실제 파일의 짧은 예 → 구현 방식의 일반성·대안·적절성 설명 → 사용자 실습 → 결과 확인 순서로 진행한다. 실습 결과와 질문을 받은 뒤 다음 회차로 넘어간다.
- 실습은 사용자가 IDE에서 직접 수행한다. 기본은 정의/참조 찾기, 중단점, 변수 관찰, 미연결 상태의 화면 조작이며 소스 수정은 하지 않는다. 앱 실행 시 자동 AWS 조회 가능성을 먼저 확인하고, 연결·조회·리소스 제어는 기본 실습에서 제외한다.
- 코드 수정 실습이 유익할 때는 목적·대상·변경 내용을 먼저 제시하고 사용자가 해당 범위를 허용한 뒤에만 진행한다. 교육 요청 자체를 코드 수정 승인으로 해석하지 않는다.

## 순서와 예상 시간

| 회차 | 주제 | 실제로 볼 파일 | 학습 후 할 수 있는 것 | 예상 |
|---|---|---|---|---|
| 1 | 전체 지도와 앱 시작: 객체 생성·연결, 계층별 역할 | `App.xaml.cs`, 각 최상위 폴더 | 앱이 어디서 시작되고 화면·서비스가 어떻게 연결되는지 설명 | 5분 |
| 2 | 화면 전환: Shell, Navigation, ContentControl, DataTemplate, DataContext | `MainWindow.xaml`, `App.xaml`, `ShellViewModel`, `NavigationService` | 화면 전환을 추적하고 화면 추가 위치 판단 | 5분 |
| 3 | 화면 안의 MVVM: 표시 값·입력·버튼 명령·변경 알림 | `DashboardView`, `DashboardViewModel`, `ViewModelBase`, `RelayCommand` | 문구·표시 항목·버튼 동작의 수정 위치 구분 | 5분 |
| 4 | 기능 하나 끝까지: 그룹 등록 → 검증 → JSON 저장·복원 | `GroupWizardViewModel`, `ServiceGroupService`, `ServiceGroup`, `GroupRules`, `IServiceGroupStore`, `JsonAppSettingsStore` | 모델·규칙·서비스·저장소의 차이와 변경 경로 이해 | 7분 |
| 5 | 공유 상태와 비동기: AWS 연결, 조회, 갱신·오류·이전 응답 처리 | `AwsConnectionService`, `AwsResourceQueryService`, `GroupStatusService`, `AwsProfileSessionFactory` | 화면 수명과 작업 수명을 구분하고 조회 기능 수정 위치 판단 | 5분 |
| 6 | 수정·추가 연습: 코드를 바꾸지 않고 변경할 파일 찾기 | 앞 회차 파일과 `doc/PROGRESS.md` | 표시 항목 변경·검증 규칙 변경·화면 추가의 작업 순서 설명 | 3분 |

총 설명 분량 약 30분, 실습은 회차별 2~3분을 더해 총 45~50분 예상. 질의응답 시간은 별도이며, 이미 이해한 내용은 짧게 복습한다.

## 회차별 직접 실습과 설계 비교

| 회차 | 사용자 실습(코드 수정 없음) | 반드시 설명할 설계 비교 |
|---|---|---|
| 1 | `App.OnStartup`에서 대시보드 생성 지점을 찾고 생성자 인자를 따라가 객체 연결을 적는다. 가능하면 중단점으로 같은 서비스 인스턴스가 전달되는지 관찰한다. | MVVM과 계층 분리는 별개. 단순 4폴더 구조와 현재 구조의 이점·탐색 비용, 직접 객체 조립과 DI 컨테이너의 차이. |
| 2 | 미연결 상태에서 `NavigateTo`에 중단점을 걸고 메뉴를 왕복한다. `CurrentViewModel`과 등록 사전을 관찰하고 View 대응 템플릿을 찾는다. | Frame/Page와 ContentControl/UserControl은 모두 가능한 선택. 현재 방식은 MVVM에서 쓰이는 패턴이며 필수는 아님. ViewModel 재사용과 View 유지·데이터 재조회는 별개임을 확인. |
| 3 | 대시보드의 표시 문구 하나와 버튼 하나를 골라 XAML 바인딩 → ViewModel 속성/명령 → 실행 메서드를 IDE에서 추적한다. | 바인딩·변경 알림·ICommand의 일반적 역할. code-behind에 적합한 UI 처리와 ViewModel에 둘 상태·동작의 경계. |
| 4 | 최종 등록 명령부터 `CreateAsync`, 검증, 저장 인터페이스, JSON 구현까지 정의/구현 찾기로 이동하며 호출 순서를 적는다. 실제 등록·파일 저장은 하지 않는다. | 모델·규칙·서비스·저장소 분리의 이유. 인터페이스의 모의 테스트 이점과 간접성 비용. 현재 규모에서 합쳐도 되는 선택과 분리할 근거. |
| 5 | 대시보드 복귀 갱신과 30초 갱신의 시작점을 찾고, 조회 중 연결이 바뀌면 결과를 버리는 조건을 소스에서 표시한다. | 공유 연결 상태가 필요한 이유, 비동기와 병렬 작업의 차이. 갱신·취소·오류 처리는 화면 전환 자체와 별도 책임임을 설명. |
| 6 | ‘카드 표시 항목 추가’, ‘그룹 이름 규칙 변경’, ‘화면 추가’ 중 하나를 골라 수정할 파일과 이유를 직접 제시한다. 코드는 바꾸지 않는다. | 매 요청에 모든 계층을 추가할 필요는 없음. 실제 요구에 필요한 최소 변경 범위를 판단하고 현재 구현의 개선 여지도 구분. |

## 일반적인 구현인지 설명하는 기준

- 각 방식에 대해 ① WPF/MVVM에서 흔한 관례인지 ② 이 프로젝트가 선택한 사항인지 ③ 현재 규모에서 얻는 이점과 비용 ④ 더 단순한 대안을 설명한다.
- 현재 구현을 정답으로 가르치지 않는다. 패턴 자체가 널리 쓰이는 것과 이 코드의 세부 구현이 적절한 것은 구분한다.
- 실제 코드에 근거해 장점뿐 아니라 복잡한 연결, 큰 ViewModel, 책임이 모인 시작 코드 등 확인되는 한계도 설명한다. 교육 중 리팩터링은 하지 않는다.
- 근거 없는 보급률이나 ‘실무에서는 무조건 이렇게 한다’는 표현을 사용하지 않는다. API 문법보다 선택 이유와 변경 시 영향을 우선한다.

## 시작 시점

- 사전 대화: 폴더별 책임과 ViewModel 중심 화면 전환의 개요를 설명함. 확인 질문으로 이해를 검증하지는 않음.
- 다음: 1회차부터 시작. `App.xaml.cs`의 객체 연결을 간단한 흐름으로 읽는다.
- 종료 기준: 사용자가 변경 요청 예시를 보고 View / ViewModel / 모델·규칙 / 서비스 / 외부 구현 중 수정할 위치와 이유를 설명할 수 있다.
- 교육 종료 이후에도 별도 개발 요청 없이 코드 수정을 자동으로 시작하지 않는다.

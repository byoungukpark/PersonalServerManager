# UI_DESIGN.md

## 1. 문서 목적과 범위

이 문서는 `REQUIREMENTS.md`와 `DEVELOPMENT_PLAN.md`를 바탕으로 WPF 데스크톱 관제 프로그램의 화면·동작 설계를 정의한다. 설계 논의에서 확정한 내용을 최종 기준으로 삼아 WPF XAML로 직접 구현한다. Figma는 사용하지 않는다. 화면 설계의 중심은 **서비스 그룹**이며, Phase 1 핵심 MVP에서 구현할 화면과 상태를 우선한다.

- **[확정 요구사항]**은 요구사항 문서에 명시된 동작·정보를 뜻한다.
- **[디자인 제안]**은 화면 배치, 표현, 탐색, 상호작용 방식의 논의 초안이다. 사용자와 합의하기 전에는 확정된 요구사항으로 취급하지 않는다.
- Phase 2 기능은 Phase 1 화면에 확장 가능한 위치만 고려한다. Phase 1 범위에 모니터링·로그의 완성 화면을 추가하지 않는다.
- UI 설계 논의가 끝나면 합의된 내용을 이 문서에 반영하고, 승인 후 WPF XAML 구현의 기준으로 사용한다. Figma 산출물은 만들지 않는다.

## 2. 핵심 정보 구조 및 내비게이션

### 2.1 정보 구조

```text
앱 시작
├─ 등록 그룹 없음 → 시작 안내 → AWS 연결 → 그룹 생성 마법사 → 그룹 목록/상세
└─ 기존 그룹 있음 → 그룹 목록 → 그룹 선택
                               ├─ AWS 재연결(마지막 프로필 우선)
                               └─ 그룹 상세 관제 및 제어
```

AWS 계정/리전 연결은 그룹을 만들고 관제하기 위해 필요하지만, 사용자의 주 탐색 단위는 서비스 그룹이다. 독립적인 전역 EC2/RDS/S3 관리 화면을 Phase 1에 추가하지 않는다.

### 2.2 데스크톱 셸

**[디자인 제안]**

- 단일 WPF 메인 창 안에서 화면을 전환해 흐름을 유지한다.
- 좌측 내비게이션: `서비스 그룹`을 기본 진입점으로 둔다. MVP에서 다른 독립 메뉴는 만들지 않는다.
- 상단 영역: 현재 화면 제목/경로, AWS 연결 상태, 활성 그룹(상세 화면일 때), 프로필 이름, 리전, 새로고침을 배치한다.
- 중앙 영역: 그룹 목록, 그룹 생성 단계 또는 선택 그룹 상세 화면을 표시한다.
- 프로필 변경, 위험 작업 확인과 같이 흐름을 잠시 멈추는 조작은 모달 대화상자 또는 명확한 확인 패널로 처리한다.
- 창 크기를 조절해도 표와 주요 제어가 잘리지 않도록 하고, 긴 리소스 목록은 중앙 영역에서 스크롤한다.

## 4. 화면별 명세

각 화면의 **확정 요구사항**은 필수 동작이고, **디자인 제안**은 논의와 합의가 필요한 시각·조작 방식이다.

### UI-01. 첫 실행 및 그룹 없음

**확정 요구사항**
- 그룹이 등록되어 있지 않으면 시작 안내를 표시한다.
- 사용자는 AWS 연결을 완료한 뒤 새 그룹 등록으로 진행한다.

**디자인 제안**
- 제목과 간단한 설명: “관리할 서비스를 그룹으로 등록하세요.”
- 주 버튼: `AWS 연결 설정`
- 보조 안내: AWS 프로필은 PC에 미리 등록되어 있어야 하며, 앱에서 Access Key를 입력하지 않는다는 설명.
- 연결 이후 `그룹 만들기`로 이어진다. 그룹이 없다는 이유만으로 빈 테이블이나 오류처럼 보이지 않게 한다.

**사용자 동작**
- `AWS 연결 설정` → UI-02.
- 등록된 그룹이 없고 아직 연결하지 않은 상태와, 연결 성공 후 그룹 등록을 기다리는 상태를 구분한다.

### UI-02. AWS 프로필 연결 및 계정 확인

**확정 요구사항**
- PC에 등록된 AWS 프로필을 선택한다. 프로필 생성·수정·삭제 및 액세스 키 직접 입력은 제공하지 않는다.
- 리전을 선택하고 연결 인증 및 AWS 계정 ID를 확인한다.
- 인증 성공과 리소스 조회/제어 권한을 혼동하지 않으며, 오류 종류를 구분한다.
- 그룹에 연결할 프로필 이름, 계정 ID, 리전을 설정 데이터에 저장하고 비밀 자격 증명은 저장하지 않는다.

**디자인 제안**
- 선택 입력: `AWS 프로필`, `리전`.
- 주 버튼: `연결 확인`; 처리 중에는 중복 실행을 막고 진행 표시를 한다.
- 연결 성공 패널에 프로필 이름, 확인된 계정 ID, 리전을 보여준다. 비밀 값은 절대 표시하지 않는다.
- 계정 ID는 부분 마스킹 여부를 디자인 결정 사항으로 남긴다(아래 §9).
- 성공 후 최초 흐름이면 `그룹 만들기`, 기존 그룹이면 해당 그룹으로 계속 진행한다.
- 프로필 목록을 읽을 수 없거나 목록이 빈 경우, 이유와 AWS 로컬 프로필 등록 후 다시 시도하도록 안내한다. 프로필 등록은 앱 안에서 하지 않는다.

### UI-03. 그룹 생성 1단계 — 그룹 정보

**확정 요구사항**
- 그룹 이름을 입력한다.
- 그룹 생성 시 AWS 프로필과 리전을 선택/확인한다.
- 그룹의 AWS 계정 ID, 리전, 마지막 사용 프로필 이름을 저장한다.

**디자인 제안**
- 단계 표시기: `그룹 정보 → 서비스 선택 → 리소스 선택 → 시작 순서 → 검토`.
- 입력: `서비스 그룹 이름`.
- 연결 요약: 프로필 이름, 계정 ID, 리전. `연결 변경`으로 UI-02를 열 수 있다.
- 주 버튼 `다음`, 보조 버튼 `취소`.
- 이름 입력 오류는 입력 영역 가까이에 표시한다. 중복 그룹명 처리 기준이 요구사항에서 정해지지 않았으므로 중복명 정책을 확정된 기능으로 만들지 않는다.

### UI-04. 그룹 생성 2단계 — 관리할 AWS 서비스

**확정 요구사항**
- EC2, RDS, S3 중 필요한 서비스를 선택한다. 어떤 서비스도 필수 선택이 아니다.
- 선택한 서비스만 실제 목록 조회를 수행한다.

**디자인 제안**
- 선택 카드 3개: EC2 인스턴스, RDS 데이터베이스, S3 버킷.
- 각 카드는 짧은 설명과 선택 상태를 제공하고, 사용자는 여러 카드를 동시에 선택할 수 있다.
- S3 카드에 `조회·모니터링만 지원` 안내를 붙인다. S3 시작·중지 제어는 제공하지 않는다.
- 선택 후 `선택한 서비스 조회` 버튼으로 명시적으로 조회한다.
- 아무 서비스도 선택하지 않은 상태에서 다음을 허용할지 여부는 요구사항상 미정이다. 서비스 미선택 그룹도 유효하다는 확정 범위와 조화되는 방식을 §9에서 결정한다.

### UI-05. 그룹 생성 3단계 — 리소스 선택

**확정 요구사항**
- 선택한 서비스의 AWS 실제 목록에서 그룹에 넣을 리소스를 고른다.
- EC2/RDS/S3를 각각 여러 개 선택할 수 있다. 리소스 ID·버킷명을 기본 흐름에서 직접 입력하지 않는다.
- 조회 성공, 빈 목록, 조회 실패, 권한 부족을 구분한다.
- 다른 그룹에 이미 등록된 리소스는 중복 추가하지 못하게 하고 안내한다.

**디자인 제안**
- 서비스별 탭 또는 섹션(EC2 / RDS / S3)으로 결과를 나눈다. 목록 열은 서비스에 맞춰 이름, 식별자, 현재 상태, 등록 가능 여부로 구성한다.
- 다중 선택 체크박스와 선택 개수를 표시한다. `새로고침`은 해당 서비스 목록을 다시 조회한다.
- 다른 그룹에 등록된 항목은 비활성화하고 “다른 그룹에서 관리 중” 표시를 한다.
- 목록 상단이나 행에 계정 ID/리전을 분명히 표시해 잘못된 계정의 리소스를 선택하지 않도록 한다.
- 서비스별 목록 로딩은 해당 영역에 표시하고, 하나의 서비스 조회 실패가 다른 서비스의 성공 결과를 지우지 않도록 시각적으로 분리하는 안을 제안한다.
- 선택된 리소스가 없는 서비스는 `선택된 리소스 없음`으로 표시한다. 오류·권한 부족은 빈 목록 문구로 대체하지 않는다.

### UI-06. 그룹 생성 4단계 — EC2/RDS 시작 순서

**확정 요구사항**
- 그룹의 EC2/RDS 시작 순서를 사용자가 지정한다.
- 그룹 전체 중지는 이 시작 순서의 역순으로 실행한다.
- 그룹에 0개 이상의 자원이 있을 수 있고 S3는 제어 시퀀스에 포함하지 않는다.

**디자인 제안**
- 선택된 EC2/RDS를 한 목록에 표시하고 우선순위 번호를 붙인다.
- 행을 드래그해 순서를 바꾸거나 `위로/아래로` 버튼을 제공한다. 접근성·사용 편의 측면에서 키보드 조작 방식을 설계 논의에서 결정한다.
- EC2와 RDS를 구분할 아이콘/라벨을 표시하고, 설정된 시작 순서와 자동 역순 중지 안내를 함께 보여준다.
- S3는 이 목록에 나타내지 않고 `그룹 관제에는 포함되지만 시작·중지 시퀀스에서는 제외`라고 설명한다.
- 제어할 EC2/RDS가 없으면 빈 상태를 보여주고 다음 단계로 진행할 수 있게 한다.

### UI-07. 그룹 생성 5단계 — 검토 및 등록

**확정 요구사항**
- 등록 정보를 저장하고 이후 재실행에도 그룹 설정을 유지한다.
- JSON에는 인증 비밀 정보를 저장하지 않는다.

**디자인 제안**
- 그룹 이름, 프로필/계정 ID/리전, 서비스별 선택 리소스 개수와 요약, 시작 순서를 읽기 전용 요약으로 보여준다.
- `이전`으로 설정을 수정하고 `그룹 등록`을 눌러 저장한다.
- 저장 중에는 중복 저장을 막고 진행 상태를 표시한다.
- 저장 성공 시 그룹 상세 관제로 이동한다. 저장 실패 시 입력한 내용은 유지하고 재시도할 수 있게 한다.
- 최종 등록 요약/검토 화면은 사용성 제안이며, 요구사항에서 필수로 정한 단계는 아니다.

### UI-08. 서비스 그룹 목록

**확정 요구사항**
- 기존 그룹을 목록으로 표시하고 선택 시 그룹 상세 관제로 이동한다.
- 그룹의 EC2/RDS 상태와 S3 조회 가능 여부 등 기본 상태를 요약한다.
- 선택된 그룹의 마지막 사용 프로필로 연결을 시도하고 계정 일치 확인 후 상태를 조회한다.
- 상태 조회 실패는 중지 상태로 표시하지 않는다.

**디자인 제안**
- 좌측 내비게이션 아래 그룹 목록을 두거나, 중앙의 그룹 카드/행 목록을 주요 콘텐츠로 둔다. 배치는 설계 논의에서 결정한다.
- 각 그룹 행/카드: 그룹 이름, 리전, 등록 자원 수, 최신 연결 상태, 기본 상태 요약, 마지막 조회 시각.
- 그룹 선택 시 상세로 이동한다. `새 그룹`은 그룹 생성 마법사를 연다.
- 기존 그룹 자동 연결 중에는 그룹별 `연결 중` 상태를 표시한다. 로컬 그룹 등록 정보는 보존한다.
- 그룹 단위 상태 요약 로직이 미정이므로, 초기 설계안은 자원별 실제 상태를 보여주고 과도한 “정상” 판정 문구는 피한다.

### UI-09. 그룹 상세 관제 및 개별 제어

**확정 요구사항**
- 그룹에 등록된 리소스의 상태를 표시한다.
- EC2 개별 시작·중지·재부팅, 지원되는 RDS 개별 시작·중지와 그룹 전체 시작·중지를 제공한다.
- S3는 조회·모니터링만 하며 시작·중지 동작은 없다.
- 작업 요청과 실제 상태 완료를 구분하고, 제어 전 사용자 확인을 받는다.

**디자인 제안 — Phase 1 최소형**
- 헤더: 그룹 이름, 계정/리전, 연결 프로필, 연결/조회 상태, 새로고침.
- 상단 제어 영역: `그룹 시작`, `그룹 중지`. 개별 제어와 시퀀스가 실행 중이면 충돌 가능한 버튼은 비활성화한다.
- 본문은 EC2 / RDS / S3 섹션으로 구분한다. 자원이 많은 경우 목록을 스크롤한다.
- 각 리소스 행은 서비스 종류, 이름, ID/식별자, AWS 현재 상태, 마지막 확인 시각을 표시한다.
- EC2 행의 동작은 `시작`, `중지`, `재부팅`; RDS 행은 `시작`, `중지`; S3 행에는 제어 버튼을 두지 않는다.
- Phase 1에는 운영 상태 및 기본 리소스 상태를 우선 표시한다. CloudWatch 그래프, S3 저장량, 로그, Health 전용 패널은 Phase 2까지 추가하지 않는다.
- 그룹 편집·삭제는 요구사항 범위에는 있지만 핵심 MVP 후 순서로 계획되어 있으므로 Phase 1 설계의 주요 동작으로 내세우지 않는다. 필요하면 그룹 목록/상세의 후속 확장점으로만 표시한다.

### UI-10. 개별/그룹 제어 확인

**확정 요구사항**
- 모든 제어 전 대상 리소스와 실행 명령을 제시하고 사용자가 확인해야 한다.
- 그룹 전체 제어는 영향을 받는 리소스를 보여준다.
- AWS 서버 시작 시 비용이 발생할 수 있음을 안내한다.

**디자인 제안**
- 모달에 동작(시작/중지/재부팅), 리소스명과 식별자, 그룹 시퀀스라면 실행 순서와 전체 대상 목록을 표시한다.
- 시작 작업에는 비용 발생 가능성을 간결히 안내한다.
- 버튼은 취소와 명시적 실행(예: `그룹 시작 실행`)으로 구분한다. 위험 작업은 색상만으로 구분하지 않는다.
- 그룹 중지 확인에는 순서가 시작 순서의 역순임을 명시한다.

### UI-11. 제어 진행 및 결과

**확정 요구사항**
- UI가 멈추지 않고 작업 중 상태를 표시한다.
- 요청 성공과 실제 상태 변경 완료를 분리한다.
- 그룹 시퀀스에서는 단계별 성공·실패·미실행을 표시한다.
- 한 단계 실패/시간 초과 시 후속 단계는 중단하며 이미 성공한 작업은 자동 롤백하지 않는다.
- 타임아웃은 AWS 명령 취소를 뜻하지 않으며 실제 상태를 다시 확인한다.

**디자인 제안**
- 단일 작업 상태 예: `요청 중 → AWS 요청 접수 → 상태 변경 확인 중 → 완료/실패/시간 초과`.
- 시퀀스 패널에 전체 진행과 각 리소스의 현재 단계, 마지막 결과를 표시한다.
- 실패 후 실행되지 않은 나머지 단계는 `미실행`으로 분명히 표시한다. 성공한 단계는 성공 상태로 남긴다.
- 시간 초과 화면에는 “AWS에서 작업이 계속 진행 중일 수 있음”과 `현재 상태 다시 확인` 동작을 안내한다.
- 동일 리소스의 제어 버튼은 진행 중 비활성화한다. 상태 표시에는 텍스트/아이콘을 함께 사용한다.

### UI-12. 연결 및 조회 오류 상태

**확정 요구사항**
- 인증 실패, 세션 만료, 프로필 부재, 계정 불일치, 권한 부족, 일반 통신/조회 오류를 가능한 범위에서 구분한다.
- 조회 실패는 리소스가 중지된 상태로 표현하지 않는다.
- 오류 때문에 앱 전체가 종료되어서는 안 된다.

**디자인 제안**

| 상태 | 화면 표현 | 사용자 동작 |
|---|---|---|
| 최초 로딩/연결 중 | 해당 영역의 진행 표시와 “연결/조회 중” | 중복 요청 방지 |
| 인증 성공 | 확인된 프로필·계정 ID·리전 표시 | 다음 단계 진행 |
| 프로필 없음 | 안내 배너와 프로필 선택 재시도 | AWS CLI에서 프로필을 준비한 후 다시 시도 |
| 인증 실패/세션 만료 | 연결 상태 오류와 재연결 버튼 | 프로필 재선택/재인증 |
| 계정 ID 불일치 | 명확한 차단 경고, 그룹 제어 비활성 | 올바른 프로필 선택 또는 취소 |
| 권한 부족 | 해당 리소스/기능 영역에 권한 부족 표시 | 다른 권한의 프로필 선택 또는 나중에 재시도 |
| 조회 실패 | 조회 실패와 마지막 성공 시각을 표시 | 해당 영역 새로고침 |
| 조회 성공, 결과 없음 | “조회된 리소스 없음” 빈 상태 | 다른 서비스 선택/다시 조회 |
| 제어 진행 중 | 리소스 및 그룹 단계 진행 상태 | 충돌 제어 비활성 |
| 제어 실패/시간 초과 | 오류 단계와 실제 상태 재조회 동작 | 상태 확인 후 사용자가 다음 작업 결정 |

프로필 권한 문제를 “리소스 없음”으로 축약하거나 계정 불일치 시 제어를 허용하지 않는다.

컴포넌트 시각 스타일은 제안이며, 동작은 대응하는 확정 요구사항을 따른다.

| 리소스 선택 표 | 그룹 생성 | 다중 선택, 이름/식별자/상태, 중복 등록 불가 사유 |
| 상태 배지 | 목록·상세·작업 결과 | 상태 텍스트와 아이콘/색상; 색상만으로 의미를 전달하지 않음 |

| 마법사 단계 표시 | 그룹 생성 | 현재 단계와 이전/다음/취소 동작 |

## 6. Phase 1 레이아웃 제안

### 6.1 기본 창 구조

**[디자인 제안]**

- 왼쪽에는 `서비스 그룹` 내비게이션과 그룹 접근을 둔다.
- 상단 바에는 현재 그룹/화면과 AWS 연결 컨텍스트를 둔다.
- 본문은 현재 작업에 필요한 그룹 목록, 마법사 또는 상세 관제 콘텐츠를 사용한다.
- 확인 대화상자와 오류 상태를 본문 흐름과 연결해 사용자가 실행 대상과 현재 상태를 놓치지 않게 한다.

### 6.2 WPF 창 및 작업 영역 기준

**[디자인 제안]**

- 설계 기준 작업 영역: 1440 × 900 px 데스크톱.
- 좁은 작업 영역 확인 기준: 1280 × 720 px.
- WPF 창 크기 조절을 전제로, 고정 폭 콘텐츠에 의존하지 않고 표 영역은 가로·세로 확장하거나 내부 스크롤하도록 설계한다.
- 위 수치는 설계 논의를 위한 기준이며 확정된 시스템 최소 해상도 요구사항은 아니다.

## 7. 시각 디자인 제안

**[디자인 제안 — 사용자와 협의 후 확정]**

- 현대적이고 간결한 WPF 관제 프로그램 스타일. 장식보다 이름·상태·실행 동작의 빠른 식별을 우선한다.
- 밝은 중립색 배경과 카드/표 영역으로 정보 위계를 두고, AWS 서비스별 구분은 작은 아이콘 또는 라벨을 사용한다.
- 상태는 텍스트+아이콘+색을 함께 사용한다. 초록/노랑/빨강의 의미는 성공/진행·주의/오류 중심으로 제안하며 세부 상태색은 설계 논의에서 결정한다.
- 기본 글꼴 크기와 버튼 크기는 장시간 데스크톱 사용에서 읽고 조작하기 쉬운 수준으로 잡는다.
- 한 화면에서 항상 보이는 상태 정보와 스크롤해야 하는 상세 목록 사이의 균형을 설계 논의에서 결정한다.
- 다크 모드는 Phase 1 요구사항이 아니므로 MVP 구현에 필수로 포함하지 않는다.

## 8. Phase 2 확장 지점

Phase 1 화면 설계에는 다음 기능을 완성된 별도 화면으로 추가하지 않는다. 그룹 상세 화면의 확장 가능한 영역만 고려한다.

- FR-009: 선택 그룹의 EC2/RDS 지표와 S3 저장 용량·객체 수를 표시할 차트/지표 영역.
- FR-010: 사용자가 선택적으로 등록한 Health URL의 응답 상태 영역.
- FR-011: 사용자가 연결한 CloudWatch Logs 그룹의 수동 조회·검색 영역.
- FR-014: 로컬 제어 기록과 앱 종료 경고 흐름.
- 전체 대시보드 요약은 Phase 1에서 그룹 목록의 기본 상태를 사용하고, Phase 2에서 풍부한 요약 UI로 확장할 수 있다.

이 확장점은 기존 화면 구조 안에서 추후 추가할 자리를 제안하는 것이며, 탭/하위 메뉴의 정확한 형태는 Phase 2 설계 전에 결정한다.

## 9. UI 설계 논의에서 결정할 사항

다음은 요구사항에서 확정하지 않은 디자인 선택이다. 사용자와 항목별로 합의하며 요구사항 범위를 임의로 확대하지 않는다.

1. 메인 셸에서 그룹 목록을 좌측 내비게이션에 둘지, 중앙 카드/표로 둘지.
2. AWS 프로필/리전을 별도 화면으로 둘지 연결 모달/패널로 둘지.
3. 계정 ID 전체 표시 또는 마스킹 방식.
4. 그룹 생성에서 서비스 미선택·자원 0개인 그룹의 다음 진행 UX.
5. 리소스 목록의 열 구성, 필터/검색 유무와 서비스별 탭 대 섹션 방식.
6. 시작 순서 조작: 드래그 정렬, 위·아래 버튼 또는 두 방식 병행.
7. 그룹 요약 상태의 라벨·아이콘·색상. 판정 로직은 요구사항 미정이므로 UI 색상만으로 의미를 고정하지 않는다.
8. 기준 창 크기와 좁은 해상도에서의 우선 정보 및 스크롤 방식.
9. 테마와 색상 팔레트, 글꼴, 여백, 모서리, 아이콘 스타일.
10. 오류 알림의 인라인 배너, 토스트 또는 대화상자 사용 기준.

## 10. Phase 1 UI 설계 완료 기준

Phase 1 UI 설계는 다음 항목을 포함하고 사용자와 합의하면 WPF XAML 구현에 착수할 수 있는 상태다.

- UI-01~UI-12 화면과 주요 상태(로딩, 권한 부족, 빈 목록, 인증/계정 오류, 제어 진행/실패/시간 초과).
- 첫 실행부터 AWS 연결, 그룹 생성, 리소스 다중 선택, 시작 순서 지정, 등록, 그룹 목록/상세 진입까지의 사용자 흐름.
- 개별 제어 확인과 그룹 순차 시작·역순 중지의 진행·결과 흐름.
- EC2/RDS/S3의 제어 가능 차이가 분명하고, AWS 자원 생성·삭제 화면이나 S3 제어 버튼이 없음.
- 확정 요구사항과 시각/레이아웃 제안이 명확히 구분됨.
- Phase 2 기능은 확장점만 고려하며 별도 완성 화면을 Phase 1 범위에 넣지 않음.

## 목적과 진행 원칙

`REQUIREMENTS.md`의 확정 요구사항은 유지하면서 구현 순서를 의존성에 맞게 나눈다. 가장 먼저 실제 AWS에 연결해 서비스 그룹을 등록하고, 그룹에 등록된 EC2/RDS를 조회·제어할 수 있는 핵심 MVP를 완성한다. 2026-10-22 사용자 요청에 따라 FR-011 CloudWatch Logs는 현재 완료 범위에서 후속 구현 예정으로 이동했다.

- **Phase 1: 핵심 MVP — 2일 집중 개발 목표**
- **Phase 2: 현재 1차 범위 완성·통합 검증 후 개발 포트폴리오 README 작성**
- **후속 구현: FR-011 CloudWatch Logs**
- **Phase 3: 기존 Backlog 및 장기 확장 기능**
- 2일은 목표 일정이며 완료 기한이 아니다. 안정성과 검증을 우선하고, Day 1 완료 조건이 충족되지 않으면 Day 2로 넘어가지 않는다.
- 각 단계에서 구현, 자동/모의 검증, 빌드 확인을 마친 뒤 다음 단계로 진행한다. 구현 완료와 실제 AWS 검증 완료를 별도로 기록한다.
- AWS 실제 시작·중지·재부팅은 명시적인 사용자 승인 없이는 실행하지 않는다. 앱 자체의 확인 창은 매번 제어 전 표시되어야 하며, 실환경 검증은 이 확인 절차와 별도로 사용자 승인을 받아야 한다.
- 승인 전에는 Mock 또는 안전한 로컬 검증을 한다. 승인되지 않은 실환경 동작은 검증 완료로 보고하지 않는다.
- 현재 단계에 필요한 구조만 설계하고 미래 기능을 위한 과도한 추상화를 피한다. 요구사항의 미정 항목은 해당 기능을 구현하기 전에 결정한다.
- UI는 사용자와 설계를 협의해 문서로 확정한 뒤 WPF XAML로 직접 구현한다. Figma 파일·시안·프로토타입은 사용하지 않는다.
- 기존 요구사항 ID를 단계에 연결한다. 요구사항 범위를 임의로 축소·삭제하지 않는다.

# Phase 1 — 핵심 MVP

## Day 1 — AWS 연동 및 서비스 그룹 관리

### 구현 순서

1. **합의된 화면 설계를 바탕으로 최소 WPF UI와 MVVM 기반 구현**
   - 현재 프로젝트 구조와 기존 구현을 확인한다.
   - 승인된 UI 설계 문서를 기준으로 화면을 WPF XAML에 직접 구현한다. 레이아웃과 공통 스타일은 ResourceDictionary로 분리한다.
   - 앱 시작 화면, 서비스 그룹 목록, 그룹 상세로 이어질 최소 탐색 흐름을 만든다.
   - View는 표시, ViewModel은 화면 상태와 명령, Service는 AWS/저장 처리로 책임을 나눈다. 현 단계에 필요한 만큼만 구조화한다.

2. **로컬 AWS 프로필 선택과 인증 확인**
   - PC에 등록된 AWS 프로필을 읽고 선택하게 한다.
   - 선택한 프로필로 AWS API 연결을 확인하고 `GetCallerIdentity` 등으로 계정 ID를 얻는다.
   - 프로필 누락, 인증 실패, 세션 만료, 권한 부족을 구분해 안내한다. 자격 증명을 앱이나 JSON에 저장하지 않는다.
   - 그룹별 리전을 지정하며 계정 ID·리전을 그룹에 저장한다. 앱 전역 활성 프로필은 연결 화면에서만 변경하고 마지막 선택 프로필은 자동 연결 없이 복원한다.

3. **EC2/RDS/S3 리소스 조회**
   - AWS 연결이 성공하면 선택한 그룹 리전과 프로필 권한으로 실제 목록을 조회한다.
   - EC2/RDS 인스턴스 및 S3 버킷의 선택에 필요한 식별자·이름·현재 상태를 표시한다.
   - 조회 오류, 권한 부족, 빈 목록을 구분하고 수동 새로고침을 제공한다.
   - 등록된 기존 리소스의 상태 조회를 위한 최소 공통 동작을 준비한다.

4. **서비스 그룹 생성 및 리소스 등록**
   - 그룹 이름 입력, EC2/RDS/S3 서비스 선택, 조회된 리소스 선택, 시작 순서 설정을 제공한다.
   - 각 자원 종류를 0개 이상 선택할 수 있게 한다.
   - 동일 AWS 리소스가 이미 다른 그룹에 등록되어 있으면 중복 등록을 막고 안내한다.
   - 그룹에 등록되지 않은 AWS 리소스를 제어할 수 있는 별도 관리 기능은 만들지 않는다.

5. **JSON 저장·복원과 기본 그룹 화면**
   - 그룹, 계정 ID, 리전, 프로필 이름, 자원 식별자 및 시작 순서를 로컬 JSON에 저장한다.
   - 앱 재실행 후 그룹을 복원하고, 그룹 목록과 등록 자원의 기본 실행 상태를 표시한다.
   - JSON에는 인증 비밀 값을 저장하지 않는다.

### 선행 조건

- AWS SDK for .NET 및 현재 WPF 프로젝트 설정을 확인한다.
- 사용할 AWS 로컬 프로필, 필요한 계정·리전, EC2/RDS/S3 읽기 권한이 준비되어야 한다.
- 계정 ID가 다르면 그룹 연결을 차단한다. S3 지역 조회·식별은 서비스별 특성을 고려한다.

### 완료 조건

- 신규 사용자가 프로필을 선택하고 AWS 연결을 확인한 뒤 그룹을 만들어 리소스를 선택·등록할 수 있다.
- 등록된 그룹과 자원 설정을 JSON에서 불러와 앱 재실행 후에도 확인할 수 있다.
- 등록 그룹 목록과 EC2/RDS/S3 기본 조회 상태가 표시된다.
- 인증·권한·조회 실패가 앱 종료로 이어지지 않는다.
- Day 1 구현의 빌드와 모의 검증이 통과한다.

### 검증 방법

- 프로필 정상/누락, 계정 ID 일치/불일치, 인증 만료, 권한 부족, 조회 성공/빈 목록/오류를 모의 응답으로 검증한다.
- 그룹 생성, 다중 자원 등록, 중복 자원 거부, JSON 저장·복원, 손상된 설정 파일 입력의 안전한 처리를 로컬에서 검증한다.
- AWS 읽기 연동은 사용자가 선택한 프로필을 사용하고 읽기 요청만 수행한다. 연결 권한이 없으면 실환경 검증을 완료한 것으로 표시하지 않는다.

### Day 1 완료 게이트

Day 1의 완료 조건이 모두 충족되어야 Day 2를 시작한다. AWS 연결이나 기본 리소스 조회가 되지 않으면 해당 의존성을 먼저 해결한다. 2일 일정 목표에 맞추기 위해 범위를 임의로 줄이지 않는다.

## Day 2 전 선행 보완 — 로컬 그룹 삭제

2026-10-21 사용자 요청으로 Phase 2 그룹 관리 범위 중 그룹 삭제만 앞당긴다. 테스트용·빈 그룹을 정리하기 위해 Day 2 제어 개발보다 먼저 구현한다. 나머지 편집 기능 우선순위는 유지한다.

- 그룹 상세에 `그룹 삭제` 버튼을 제공하고 그룹명과 AWS 자원 유지 안내를 확인 모달에 표시한다.
- 확인 후 GUID 기준 로컬 그룹·연결 정보만 JSON에서 삭제한다. AWS API를 호출하지 않으며 미연결·계정 불일치 상태에서도 삭제 가능하다.
- 저장 성공 후 목록·상태 캐시에서 제거하고 대시보드로 이동한다. 진행 중 조회의 늦은 결과가 그룹을 다시 반영하지 않게 한다.
- 취소·저장 실패 시 기존 그룹을 유지하고 오류를 표시한다. 삭제된 그룹의 자원은 다른 그룹에 다시 등록할 수 있다.
- 완료 조건: 빈/자원 포함 그룹 삭제, 확인 취소, 저장 실패, 재실행 후 삭제 유지, 자원 재등록 및 조회 중 삭제를 로컬/Mock으로 검증하고 빌드한다.
- 위 보완 완료 후 Day 2를 시작한다. 제어 기능 도입 시 제어 중 삭제 차단도 함께 적용한다.

## Day 2 — AWS 개별·그룹 제어 및 실제 동작 검증

### 구현 순서

1. **개별 제어**
   - 그룹에 등록된 EC2 시작·중지·재부팅을 제공한다.
   - 그룹에 등록된 RDS는 AWS에서 지원되는 경우 시작·중지를 제공한다.
   - 명령 전 대상과 동작을 확인받고, 작업 중인 리소스의 중복 제어를 막는다.

2. **요청 결과와 실제 상태 전이 구분**
   - AWS API가 요청을 접수했는지와 리소스가 목표 상태에 실제로 도달했는지를 각각 표시한다.
   - 완료·실패까지 상태를 조회하고, 권한 부족·통신 실패·미지원 작업을 가능한 범위에서 구분한다.
   - 2026-10-21 사용자 확정: EC2는 5초, RDS는 15초 간격으로 상태를 확인한다. EC2 제한시간은 1~60분(기본 10분), RDS는 1~120분(기본 30분)이며 최소 설정 화면·JSON 저장을 개별 제어와 함께 구현한다.
   - EC2 재부팅은 사용자 합의에 따라 `요청 접수 · 재부팅 완료 미확인`으로 종료한다. `running` 관측을 재부팅 완료로 판정하지 않는다.
   - 개별 제어 단계부터 전역 진행 표시·최근 결과 5건·화면 이동 중 실행 유지·종료 경고와 제어 중 연결 변경/재확인·삭제 차단을 적용한다. 그룹 시퀀스·남은 단계 취소는 이후 Day 2 작업이다.

3. **그룹 전체 시작(C-1)**
   - 사용자가 지정한 순서대로 EC2/RDS를 한 번에 하나씩 처리한다.
   - 현재 상태가 이미 목표 상태면 명령 없이 건너뛴다.
   - 한 자원의 목표 상태 도달을 확인한 뒤 다음 자원으로 진행한다. S3는 제어 시퀀스에서 제외한다.

4. **그룹 전체 중지**
   - 시작 순서의 역순으로 EC2/RDS를 완전 순차 처리한다.
   - Spring Boot 개별 종료 명령은 보내지 않는다. OS/systemd 및 서버 측 종료 동작에 의존한다.

5. **실패·시간 제한·안전 처리**
   - EC2 시작/중지 기본 10분, RDS 시작/중지 기본 30분으로 적용하고 앱 설정에서 종류별로 변경 가능하도록 한다.
   - 단계 실패 또는 시간 초과 시 즉시 중단하고 후속 작업을 실행하지 않는다.
   - 이미 성공한 작업은 유지하고 자동 롤백하지 않는다. 성공·실패·미실행 단계를 구분해 표시한다.
   - 시간 초과가 AWS 명령 취소를 뜻하지 않음을 안내하고 가능한 범위에서 실제 상태를 다시 조회한다.
   - 앱 전체 동시 제어 작업을 1건으로 제한하고, 제어 중 프로필 변경/연결 해제를 막는다. 화면 이동 중 제어는 지속한다.
   - 사용자가 확인 후 남은 단계만 취소할 수 있게 한다. 현재 제출된 AWS 명령은 취소·롤백하지 않는다.

### 선행 조건

- Day 1 완료 게이트 및 로컬 그룹 삭제 선행 보완 완료.
- 변경 상태별 동작과 각 리소스의 정상 대기 상태를 확인할 수 있어야 한다.
- 실제 제어 전에 Mock으로 정상·오류·지연·시간 초과 흐름을 검증한다.

### 완료 조건

- 개별 EC2 시작·중지·재부팅과 지원되는 RDS 시작·중지가 확인 창 및 중복 방지를 거쳐 동작한다.
- 그룹 시작/중지가 사용자 지정 순서와 역순을 지키며 엄격히 순차 실행된다.
- 요청 접수와 실제 상태 변경 완료가 구분되고, 실패·시간 초과 시 후속 단계가 중단된다.
- Mock 검증과 빌드가 통과한다.
- 기존 UKart AWS 환경에서 실제 제어를 검증한 경우, 사용자가 승인한 대상·작업과 관찰 결과를 기록한다. 실제 제어 승인이 없으면 실환경 검증 상태를 **대기**로 남기고 검증 완료로 보고하지 않는다.

### 검증 방법

- Mock으로 확인 취소, 요청 접수, 상태 변경 완료, 이미 목표 상태, 미지원 RDS 작업, 권한 부족, 네트워크 실패, 지연, 시간 초과, 중간 단계 실패 및 후속 단계 중단을 검증한다.
- 실 AWS 검증은 앱의 제어 확인 창과 별도로, 사용자가 정확한 대상 리소스와 허용 작업을 승인한 뒤에만 수행한다. EC2/RDS의 시작·중지 비용과 서비스 영향도 고려하고 결과를 기록한다.

### Phase 1 종료 게이트 — 핵심 MVP

- Day 1 및 Day 2 완료 조건을 모두 충족한다.

## 2.2 자동 상태 갱신과 상세 CloudWatch 모니터링

**2026-10-22 범위 변경(사용자 요청, 구현):** Health Check 착수 전에 FR-009의 확정 지표를 EC2 4종·RDS 6종·S3 2종으로 확대한다. EC2 송수신은 독립 카드로 분리하고, 그리드(한 줄 2개 고정)/스택(한 줄 1개) 선택과 가용 너비 채우기, 그래프 확대·축소/이동 비활성화를 적용한다. 변경 사유는 사용자 실사용 확인에서 발견한 카드 오른쪽 여백과 지표 확장 요청이다. 이후 단계 순서는 유지한다.

상태 검사는 최신 0/1을 정상/실패 배지로 보여주고, 과거 0·1은 계단형 그래프로 표시한다. 데이터 없음은 정상과 구분한다. 그리드/스택 전환은 기존 측정값만 재배치한다.

추가 검증: 모든 지표의 단위·통계·빈 데이터, 2열/1열 전환과 창 크기 변경 시 너비·잘림, 휠 입력 시 그래프 범위 불변과 화면 세로 스크롤, 탭 재진입 및 배치 전환 시 PlotModel 중복 연결 방지를 확인한다. 새 지표의 실제 AWS 응답·호출량은 기존 지표 확인과 구분해 기록한다.

**요구사항:** FR-008, FR-009, NFR-002, NFR-003

**구현 대상**
- 모든 그룹의 상태 요약, 마지막 정상 수집 시각, 조회 실패의 구분.
- EC2/RDS 상태 30초, 애플리케이션 Health 30초, EC2/RDS 성능 지표 5분 갱신.
- EC2 CPU·네트워크, RDS CPU·DB 연결 수, S3 저장 용량·객체 수(일 단위)를 그룹 상세에서 표시한다.
- 2026-10-22 사용자 확정: 선택 리소스 하단의 모니터링을 그룹 상세 상단의 `그룹 모니터링` 탭으로 옮긴다. 상단은 `리소스 상세 · 개별 제어 | 그룹 모니터링` 두 탭만 두고, 기존 EC2/RDS/S3 선택·기본 정보·개별 제어는 첫 탭 안에 유지한다. 모든 등록 리소스의 그래프를 카드로 나열하고 새 지표 카드 추가가 가능한 구성으로 만든다. 이는 2.2 내부의 UI 범위 조정이며 이후 단계의 우선순위는 변경하지 않는다.
- API 중복 호출을 줄이고 앱 종료 시 자동 갱신을 중단한다.

**완료 조건**
- 일정 주기로 갱신되어도 UI가 응답하고, 미수집·지연·오류를 중지 상태와 구분한다.
- 그룹 모니터링에서 등록된 모든 리소스의 카드를 볼 수 있고, 리소스 상세의 개별 제어·기본 정보가 기존대로 동작한다.

**검증 방법**
- Mock으로 지표 정상/빈 데이터/지연/권한 오류, 자동 갱신 중 취소·종료, 측정 시각·단위를 검증한다.

- EC2/RDS/S3 외 AWS 서비스

## 단계 간 진행 및 변경 관리

각 단계의 완료 조건과 검증을 확인한 뒤 다음 단계로 진행한다. Day 1 미완료 시 Day 2를 시작하지 않고 선행 기능을 해결한다. Phase 1에서 실제 운영 검증이 승인 대기라면 해당 상태를 명확히 남긴다. 요구사항이나 우선순위 변경이 필요하면 임의로 범위를 줄이지 말고 관련 문서와 사용자 결정을 먼저 반영한다.

## 설계 협의 반영 기준

- 질문 1~100의 최종 합의는 `UI_DESIGN.md`에 화면/상호작용 기준으로, `REQUIREMENTS.md`에 기능·안전·저장 정책으로 반영되어 있다. 이 단계 계획은 **구현 순서**이며 Phase 2 상세 화면까지 Day 1~2에 구현하라는 뜻이 아니다.
- JSON 그룹·앱 설정, SQLite 제어 이력 분리를 따른다. JSON 손상 시 자동 초기화가 아니라 안내 후 종료한다.
- AWS 계정과 리전을 그룹에 결합하되 프로필은 **앱 전역 1개만 활성화**한다. 앱 시작 시 자동 연결하지 않는다.
- 개별/그룹 제어의 타임아웃은 EC2 10분·RDS 30분을 기본값으로 설정에서 변경 가능하게 한다. 실패·시간 초과는 후속 단계 즉시 중단, 사용자 취소는 남은 단계 중단이며 자동 롤백은 없다.

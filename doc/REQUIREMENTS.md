# REQUIREMENTS.md

## 1. 프로젝트 개요와 범위

### 1.1 목적

C# WPF와 MVVM을 사용하는 Windows 로컬 데스크톱 앱으로, 사용자가 AWS에서 이미 생성한 리소스를 **서비스 그룹**으로 묶어 상태를 관제하고 필요한 실행 제어를 한다. 최초 실사용 검증 대상은 기존 UKart AWS 환경이다.

AWS 리소스를 생성·삭제하거나 배포하는 도구가 아니다. 사용자는 자신이 관리하는 서버/서비스를 그룹으로 만들고, 그 그룹에 필요한 AWS 자원을 연결한다. AWS 연결과 리소스 조회는 그룹을 구성하고 관제하기 위한 내부 공통 기능이며, 일반 사용 흐름은 서비스 그룹을 중심으로 한다.

### 1.2 기술 및 운영 환경

| 항목 | 내용 | 상태 |
|---|---|---|
| 개발 언어 / UI | C# / WPF | 확정 |
| 설계 패턴 | MVVM | 확정 |
| UI 설계·구현 | UI 설계 내용을 확정한 뒤 WPF XAML로 직접 구현. Figma는 사용하지 않음 | 확정 |
| AWS 연동 | AWS SDK for .NET | 확정 |
| 실행 환경 | Windows 로컬 PC | 확정 |
| AWS 인증 | PC에 이미 등록된 AWS 로컬 프로필 | 1차 확정 |
| 설정 저장 | 로컬 JSON 파일 | 확정 |
| 최초 실사용 검증 | 기존 UKart AWS 환경 | 확정 |

화면 레이아웃과 공통 스타일은 WPF XAML 및 `ResourceDictionary`로 구성한다. UI 설계 논의에서 확정한 내용을 기준으로 구현하며, Figma 파일·시안·프로토타입은 산출물이나 구현 경로로 사용하지 않는다.

### 1.3 1차 지원 서비스와 제어 범위

1차 구현에서 지원하는 AWS 서비스는 EC2, RDS, S3로 한정한다.

- **EC2:** 상태 조회, 시작, 중지, 재부팅
- **RDS:** 상태 조회, AWS가 지원하는 인스턴스의 시작·중지
- **S3:** 버킷 조회 및 모니터링. 시작·중지 제어는 하지 않는다.
- AWS 리소스 생성·삭제는 제공하지 않는다.
- S3 객체의 업로드·수정·삭제는 제공하지 않는다.
- 서비스 그룹 삭제 또는 그룹에서 리소스 연결 해제는 실제 AWS 리소스에 영향을 주지 않는다.
- 1차 구현의 개별 관제·제어 범위는 서비스 그룹에 등록된 리소스다. 그룹 밖 리소스의 개별 관제·제어는 추후 기능이다.

### 1.4 요구사항 상태 표기

- **[MVP 확정]**: 1차 구현 범위에 포함하는 확정 요구사항
- **[Backlog 확정]**: 추후 구현 대상으로 확정했으나 1차 구현에서는 제외하는 기능
- **[미정]**: 사용자 결정 또는 추가 정보가 필요하며 임의로 구현하지 않는 항목
- **[구현 시 검토]**: 요구사항의 목적은 확정했으나 구체 구현 방법을 해당 기능 단계에서 검토할 항목

## 2. 서비스 그룹 중심 사용자 흐름

### FR-012. 기본 화면 및 사용 흐름

**[MVP 확정]**

#### 최초 실행 및 그룹 등록

1. 프로그램을 실행한다.
2. 등록된 그룹이 없으면 시작 안내 화면을 표시한다.
3. AWS 연결을 설정하고 인증을 확인한다.
4. 새 서비스 그룹을 만든 뒤 이름을 입력한다.
5. 그룹에서 관리할 AWS 서비스(EC2, RDS, S3)를 필요한 만큼 선택한다. 선택은 선택 사항이며 그룹에 특정 서비스가 반드시 있어야 하는 것은 아니다.
6. 선택된 AWS 서비스의 실제 리소스 목록을 조회한다.
7. 사용자가 관리 대상 인스턴스와 버킷을 선택한다.
8. EC2/RDS 시작 시퀀스를 설정한다.
9. 그룹을 등록하고 그룹 상세 관제 화면으로 이동한다.

리소스 ID나 버킷 이름을 일일이 입력하는 방식은 기본 등록 흐름으로 삼지 않는다.

#### 기존 그룹 사용

1. 프로그램 실행 후 등록된 서비스 그룹 목록을 표시한다.
2. 사용자가 그룹을 선택한다.
3. 그룹에서 마지막으로 사용한 AWS 프로필로 연결을 시도한다.
4. 인증과 계정 일치 여부를 확인한 후 해당 그룹의 리소스 상태를 조회한다.
5. 그룹 상세 관제 및 제어 기능을 제공한다.

전체 대시보드는 여러 그룹의 상태를 요약한다. 그룹을 선택하면 그 그룹의 상세 관제 화면으로 이동한다. AWS 프로필 및 전체 AWS 리소스 목록은 그룹 중심 흐름을 지원하는 공통 기능으로 제공한다.

#### 공통 UI 동작

- 장시간 AWS 작업 중에도 UI가 응답해야 한다.
- 작업 중, 성공, 실패, 시간 초과 상태를 구분한다.
- 위험한 제어는 실행 전에 사용자가 확인한다.
- 조회 실패가 프로그램 종료로 이어지지 않아야 한다.

## 3. AWS 인증 및 연결

### FR-001. AWS 프로필 연결

**[MVP 확정]**

- PC에 이미 등록된 AWS 로컬 프로필 목록을 조회하고, 사용자가 프로필을 선택할 수 있다.
- AWS SDK는 선택된 프로필에 설정된 IAM 사용자 또는 역할의 권한으로 AWS API를 호출한다.
- 앱은 프로필 자체를 생성·수정·삭제하지 않는다.
- 액세스 키를 직접 입력받거나 저장하는 기능은 제공하지 않는다.
- 자격 증명은 소스코드나 그룹 설정 JSON에 저장하지 않는다. JSON에는 프로필 이름 등 연결 참조 정보만 저장한다.
- 연결 인증의 성공과 각 작업에 필요한 API 권한의 보유 여부를 구분한다. 권한 부족은 AWS API 실제 응답으로 판단해 안내한다.
- 인증 실패, 세션 만료, 프로필을 찾을 수 없는 경우, 권한 부족을 구분해 안내한다.

### FR-001.1. 그룹과 프로필·계정·리전 연결

**[MVP 확정]**

- 서비스 그룹과 AWS 프로필은 독립적으로 관리한다.
- 그룹을 만들 때 사용할 AWS 프로필과 AWS 리전을 지정한다.
- 그룹 설정에는 AWS 계정 ID, AWS 리전, 마지막 사용 프로필 이름, 등록 리소스 식별자를 저장한다. 자격 증명 값은 저장하지 않는다.
- 그룹 진입 시 마지막 사용 프로필로 연결을 시도하고, 사용자는 다른 로컬 프로필을 선택할 수 있다.
- AWS STS `GetCallerIdentity` 등으로 현재 연결의 AWS 계정 ID를 확인한다.
- 현재 계정 ID가 그룹에 저장된 계정 ID와 다르면 해당 그룹의 연결을 차단한다. 다른 프로필을 선택해도 계정 ID가 같으면 그룹의 리소스 등록 정보는 유지한다.
- 그룹에 저장된 리전을 사용해 지역별 리소스를 조회한다.
- 제어 작업이 진행 중이면 프로필 변경을 제한한다.
- 인증 성공만으로 모든 리소스의 조회·제어 권한을 보장한다고 표시하지 않는다. 각 작업의 실제 권한에 따른 결과를 표시한다.

**[구현 시 검토]** S3 버킷의 지역 정보와 버킷 이름의 식별 특성은 EC2/RDS의 지역별 식별과 다를 수 있으므로, 그룹의 리전 적용 및 중복 판단 시 서비스별 조회·식별 방법을 반영한다.

### FR-001.2. 인증 확장

**[Backlog 확정]**

- IAM Identity Center(SSO)를 이용한 인증 지원
- 임시 자격 증명 인증 방식 확장
- EC2 DryRun 또는 IAM Policy Simulator 등을 이용한 리소스별 권한 사전 검사와 UI 표시

인증 내부 구조는 향후 프로필 기반 SSO를 추가할 수 있도록 고려한다. 1차 구현에서 SSO 또는 사전 권한 검사 기능을 제공하는 것으로 간주하지 않는다.

## 4. AWS 리소스 조회와 그룹 등록

### FR-002. 리소스 발견 및 선택

**[MVP 확정]**

- 사용자가 그룹 등록 과정에서 EC2, RDS, S3 중 필요한 서비스를 선택하면 AWS SDK로 해당 계정·리전의 실제 리소스를 조회한다.
- 사용자는 조회된 EC2 인스턴스, RDS 인스턴스, S3 버킷 중 그룹에서 관리할 항목을 선택한다.
- 사용자가 서비스를 선택하지 않으면 해당 서비스 조회를 요구하지 않는다.
- 조회 실패, 권한 부족, 리소스 목록이 비어 있음은 서로 구분해 안내한다.
- 이름, 식별자, AWS가 제공하는 현재 상태 등 등록 대상을 알아보는 데 필요한 정보를 표시한다.
- 수동 새로고침을 제공한다.
- S3는 조회 및 모니터링 대상이며 실행 제어 대상이 아니다.

### FR-003. 서비스 그룹 관리 및 자원 연결

**[MVP 확정]**

- 사용자는 여러 서비스 그룹을 만들고 각 그룹에 이름을 지정할 수 있다.
- 한 그룹에는 EC2 인스턴스, RDS 인스턴스, S3 버킷을 각각 0개 이상 연결할 수 있다.
- 그룹 생성 시 서비스 선택 및 AWS 조회 결과에서 관리 대상을 고른다. 그룹에 특정 AWS 서비스가 반드시 포함되어야 하지 않는다.
- 그룹 이름 변경, 리소스 추가, 리소스 연결 해제, EC2/RDS 시작 순서 변경, AWS 프로필 변경, 그룹 삭제를 지원한다.
- 리소스 연결 해제와 그룹 삭제는 로컬 그룹 설정에만 반영하며 AWS 리소스를 중지·삭제하지 않는다.
- 등록된 리소스가 AWS에서 삭제되거나 현재 접근 불가능해도 앱이 비정상 종료되지 않도록 한다.

### FR-003.1. 그룹 간 리소스 중복

**[MVP 확정]**

- 동일 AWS 리소스를 서로 다른 서비스 그룹에 중복 등록하지 않는다.
- EC2, RDS, S3 각각에 중복 등록 제한을 적용한다.
- 이미 다른 그룹에 연결된 항목은 등록 과정에서 사용자에게 알린다.
- 중복 여부는 AWS 계정과 리소스 식별자를 고려하며, 지역별 리소스와 S3 버킷의 식별 특성을 구분한다.

**[Backlog 확정]**

- AWS 태그를 이용한 리소스 검색 및 그룹 연결 편의 기능
- 동일 리소스의 그룹 간 중복 연결 허용
- 공유 리소스 자동 보호 정책. 다른 그룹에서 사용 중인 리소스에 대한 그룹 전체 중지 동작을 제한하는 방향으로 검토한다. 실제 애플리케이션 사용 여부를 자동 판별하는 요구사항은 아니다.

## 5. 개별 EC2/RDS 제어

### FR-004. EC2 개별 제어

**[MVP 확정]**

- 그룹에 등록된 EC2 인스턴스의 상태를 확인한다.
- 시작, 중지, 재부팅을 요청할 수 있다.
- 제어 전에 대상과 명령을 보여주고 사용자 확인을 받는다.
- AWS 요청 접수 결과와 실제 상태 변경 완료를 구분한다.
- 작업 완료 또는 실패까지 상태를 추적한다.
- 영구 종료(Terminate) 기능은 제공하지 않는다.

### FR-005. RDS 개별 제어

**[MVP 확정]**

- 그룹에 등록된 RDS 인스턴스의 상태를 확인한다.
- AWS가 시작·중지를 지원하는 RDS 인스턴스에 대해서만 해당 작업을 요청한다.
- 제어 전에 대상과 명령을 보여주고 사용자 확인을 받는다.
- 상태 변경 과정과 최종 결과를 표시하고, AWS가 지원하지 않는 작업은 실행하지 않고 사유를 안내한다.
- RDS 삭제 기능은 제공하지 않는다.
- 상태 변경 중 같은 리소스에 중복 제어 요청을 보내지 않는다.

### 제어 승인 및 범위

**[MVP 확정]**

- EC2/RDS 실제 시작·중지·재부팅 요청은 사용자가 해당 작업을 확인한 뒤에만 보낸다.
- 자동 갱신, 상태 조회, 로그 조회가 제어 명령을 발생시키지 않도록 한다.
- 그룹에 등록되지 않은 리소스는 1차 구현의 개별 제어 대상이 아니다.

## 6. 서비스 그룹 통합 제어

### FR-006. 그룹 전체 시작

**[MVP 확정]**

- 사용자는 그룹의 EC2/RDS 시작 순서를 직접 지정한다. 그룹에 등록된 제어 대상 리소스들을 한 번에 하나씩, 사용자가 지정한 순서로 처리한다.
- 한 리소스의 AWS 실제 상태가 원하는 실행 상태에 도달한 것을 확인한 후 다음 리소스에 명령한다.
- 병렬 실행은 지원하지 않는다.
- 이미 원하는 상태인 리소스는 명령을 보내지 않고 건너뛴다.
- S3는 제어 시퀀스에서 제외한다.
- 시퀀스 시작 전에 영향을 받는 리소스와 시작 명령을 표시하고 사용자 확인을 받는다.
- 단계별 진행, 성공, 실패, 미실행 결과와 전체 결과를 표시한다.

### FR-007. 그룹 전체 중지

**[MVP 확정]**

- 그룹 전체 중지 순서는 사용자가 설정한 시작 순서의 역순으로 자동 결정한다. 시작·중지 순서를 별도로 설정하지 않는다.
- 각 리소스를 순차 처리하고 실제 상태를 확인한 다음 다음 리소스로 진행한다. S3는 제외한다.
- 시퀀스 시작 전에 영향을 받는 리소스와 중지 명령을 표시하고 사용자 확인을 받는다.
- Spring Boot 애플리케이션 개별 정상 종료 명령을 보내지 않는다. EC2 종료 과정은 OS/systemd의 종료 동작 및 서버 측 설정에 의존한다.

### FR-006/007. 실패·시간 초과 처리

**[MVP 확정]**

- 한 단계가 실패하거나 제한 시간을 넘으면 시퀀스를 즉시 중단하고 후속 단계를 실행하지 않는다.
- 앞서 성공한 작업은 자동으로 되돌리지 않는다.
- 성공, 실패, 미실행 단계의 결과를 구분해 표시한다.
- 실패 또는 시간 초과 후 가능한 범위에서 실제 AWS 상태를 다시 조회한다.
- AWS 명령 요청 성공과 실제 상태 변경 완료를 구분한다.
- 기본 제한 시간은 다음과 같다.

| 리소스 | 시작 | 중지 |
|---|---:|---:|
| EC2 | 5분 | 5분 |
| RDS | 15분 | 15분 |

제한 시간 만료는 이미 AWS에 제출한 명령의 취소를 의미하지 않는다. 후속 시퀀스만 중단하고 리소스의 실제 상태를 다시 확인한다.

**[Backlog 확정]**

- 동일 단계에서 여러 리소스 병렬 실행(C-2)
- 시작 순서와 중지 순서 개별 설정
- 리소스별 제한 시간 사용자 설정
- 복잡한 리소스 의존 관계 및 제어 정책

## 7. EC2 내부 애플리케이션 상태

### FR-010. Health Check

**[MVP 확정]**

- EC2 인스턴스 상태와 EC2 안에서 실행되는 애플리케이션의 HTTP 응답 상태를 별도로 표시한다.
- 애플리케이션 Health Check 등록은 선택 사항이며 등록하지 않아도 그룹 생성·관제가 가능하다.
- 사용자는 애플리케이션 이름과 Health URL을 등록할 수 있다.
- 앱은 HTTP 요청으로 응답을 확인하고 정상 응답, 오류 응답, 연결 실패, 확인 불가를 구분한다.
- EC2가 Running이라는 이유만으로 애플리케이션이 정상이라고 판단하지 않는다.
- HTTP 응답 확인 결과와 애플리케이션 자체 Health 판정을 구분한다.
- 기본 30초 주기로 확인하고 수동 새로고침도 제공한다.
- 특정 프레임워크에 고정적으로 종속시키지 않는다. UKart에서는 Spring Boot Actuator Health 사용을 우선 검토한다.
- URL 공개 범위와 접근 통제를 고려한다.

**[MVP 확정] 애플리케이션 제어 범위**

- Spring Boot 등 EC2 내부 애플리케이션의 개별 시작·중지·재시작 기능은 제공하지 않는다.
- EC2 부팅 시 systemd가 UKart의 Spring Boot 앱을 자동 시작하는 서버 측 정책은 유지하되, WPF가 이를 설치·구성하지 않는다.
- 그룹 전체 중지 시 Spring Boot 개별 종료 API/명령은 호출하지 않고 EC2 중지를 요청한다. 정상 종료는 OS/systemd 종료 동작과 서버 설정에 의존한다.

**[Backlog 확정]** EC2 내부 애플리케이션을 AWS Systems Manager(SSM) 등으로 개별 시작·중지·재시작하는 기능을 검토한다.

## 8. 상태 및 성능 모니터링

### FR-008. 리소스 상태

**[MVP 확정]**

- 전체 대시보드에서 모든 그룹의 EC2/RDS 현재 상태와 S3 조회 가능 여부 등 기본 상태를 요약한다.
- 선택 그룹 상세 화면에서 그룹에 등록된 리소스별 상태를 표시한다.
- 그룹 요약은 정상, 일부 중지, 조회 실패 등 상태를 구분한다. 세부 판정 기준은 미결정 사항으로 둔다.
- 조회 실패는 리소스가 중지된 상태로 표시하지 않는다.
- 실패 시 마지막 정상 수집 시각과 오류를 표시한다.
- 상태 조회를 자동·수동으로 갱신한다. 프로그램이 종료되면 자동 갱신을 중단한다.
- API 중복 호출을 줄이기 위한 상태 캐시를 고려하고, 상세 성능 지표는 활성 그룹을 중심으로 조회한다.

### FR-009. CloudWatch 성능 지표

**[MVP 확정]**

선택한 그룹의 상세 화면에서 다음 정보를 표시한다.

- **EC2:** CPU 사용률 그래프, 네트워크 송수신량
- **RDS:** CPU 사용률, DB 연결 수
- **S3:** 버킷 기본 정보, 저장 용량, 객체 수
- 지표 측정 시각, 단위, 데이터 없음·지연 상태
- 등록된 애플리케이션의 Health 상태, 마지막 확인 시각 및 조회 오류

S3 저장 용량과 객체 수는 일 단위 CloudWatch 지표 특성을 고려한다. 데이터 지연·미수집 상태를 표시하며, 이 지표의 객체 수가 현재 파일 목록의 개수와 항상 같다고 가정하지 않는다.

### 갱신 주기

**[MVP 확정]**

| 조회 대상 | 기본 주기/방법 |
|---|---|
| EC2/RDS 상태 | 30초 |
| 등록 애플리케이션 Health | 30초 |
| EC2/RDS CloudWatch 성능 지표 | 5분 |
| S3 저장 용량·객체 수 | 일 단위 지표에 맞춰 조회 |
| CloudWatch Logs | 수동 새로고침 |

- 자동 갱신은 프로그램 실행 중에만 동작하며, UI 비동기 처리로 응답성을 유지한다.
- AWS API 오류로 앱 전체가 종료되지 않아야 한다.
- API 호출량 및 비용을 고려한다.

**[Backlog 확정]** 갱신 주기 사용자 설정, EC2 메모리·디스크, RDS 상세 지표, HTTP 요청량·오류율, 고급 모니터링 및 통계 분석.

## 9. CloudWatch Logs

### FR-011. 로그 그룹 선택 및 조회

**[MVP 확정]**

- AWS 프로필 권한으로 CloudWatch Logs 로그 그룹 목록을 조회한다.
- 사용자가 로그 그룹을 골라 서비스 그룹에 연결한다.
- 이미 CloudWatch Logs에 수집된 로그를 WPF에서 조회한다. 로그 그룹과 EC2 인스턴스가 반드시 일대일이라고 가정하지 않는다.
- 최근 100건을 기본으로 표시한다.
- 로그 발생 시각과 메시지를 표시하고 키워드 및 로그 레벨 검색을 제공한다.
- 기본 조회 방식은 수동 새로고침이다.
- 조회 실패와 권한 부족을 안내한다.
- 로그를 CloudWatch로 보내는 서버 측 설정은 사용자가 별도로 구성한다.

**[MVP 제외]** CloudWatch Agent 자동 설치, 로그 수집 환경 자동 구성, 실시간 로그 스트리밍, 고급 로그 분석.

**[Backlog 확정]** EC2 관련 로그 그룹 자동 검색·연결, 서버 로그 수집 환경 자동 구성, 실시간 로그 조회, 고급 검색·통계.

## 10. 설정 및 로컬 작업 기록

### FR-013. 설정 저장

**[MVP 확정]** 설정은 로컬 JSON 파일에 저장하고 앱 재실행 후 유지한다. 저장 대상은 다음과 같다.

- 서비스 그룹 정보와 그룹 이름
- AWS 계정 ID, 리전, 마지막 사용 AWS 프로필 이름
- 그룹에 연결된 리소스 식별자
- EC2/RDS 사용자 지정 시작 순서
- 애플리케이션 이름과 Health URL 설정
- CloudWatch Logs 연결 설정

AWS 액세스 키, 시크릿 키 및 기타 AWS 인증 비밀 정보는 설정 파일에 저장하지 않는다. 설정 파일 오류가 앱 비정상 종료로 이어지지 않도록 한다.

### FR-014. 제어 작업 기록

**[MVP 확정]** 실제 제어 작업의 로컬 기록에 다음을 저장한다.

- 작업 대상과 실행 명령
- 요청 시각
- AWS 요청 성공·실패
- 실제 상태 변경 성공·실패
- 시간 초과 및 오류 정보

민감한 AWS 자격 증명은 기록하지 않는다. 로컬 작업 기록의 파일 형식과 보존 정책은 미결정 사항이다.

## 11. 제어 안전·오류 처리

### NFR-001. 보안 및 안전

**[MVP 확정]**

- AWS 자격 증명을 소스코드, 그룹 JSON 설정 및 작업 로그에 넣지 않는다.
- 각 작업은 선택된 로컬 프로필 권한을 따른다. 필요한 AWS 권한만 부여하는 방향을 유지한다.
- 모든 개별 EC2/RDS 제어와 그룹 전체 시작·중지는 실행 전 사용자 확인을 받는다.
- 확인 화면에는 대상 리소스와 실행 명령을 표시한다.
- 작업 중인 리소스에 중복 명령을 보내지 않는다.
- 그룹 시퀀스 실행 중 충돌할 수 있는 개별 제어를 제한한다.
- 제어 작업 중 AWS 프로필 변경을 제한한다.
- 그룹 또는 리소스 연결을 삭제해도 AWS 리소스를 중지·삭제하지 않는다.

### NFR-002. 비용 관리

**[MVP 확정]**

- 불필요한 반복 API 호출을 피하고 갱신 주기와 로그 조회 범위를 제한한다.
- 실제 AWS 리소스에 명령을 보내는 테스트는 사용자가 승인한 대상에서만 수행한다.
- 서버 시작 시 비용이 발생할 수 있음을 안내한다.
- 리소스 중지 후에도 일부 AWS 리소스에는 비용이 발생할 수 있음을 안내한다.

### NFR-003. 오류 및 작업 상태

**[MVP 확정]**

- 인증 실패, 세션 만료, 권한 부족, 통신 오류, AWS 작업 실패와 시간 초과를 가능한 범위에서 구분한다.
- AWS 작업의 요청 접수와 실제 상태 완료를 구분한다.
- 작업 진행 상태를 표시하고 실패한 요청을 무한히 재시도하지 않는다.
- 그룹 시퀀스 실패 시 성공·실패·미실행 결과를 구분하고 후속 단계를 중단한다.
- 프로그램 종료 시도 중 제어 작업이 진행 중이면 경고한다.
- AWS에 이미 제출된 명령은 앱 종료 뒤에도 진행될 수 있음을 안내한다.

## 14. 남은 미결정 사항

아래 항목은 임의로 결정하지 않고 관련 기능을 구현하기 전에 사용자와 협의한다.

- 여러 리소스가 섞인 그룹의 정상·일부 중지·오류 요약 판정 기준
- 애플리케이션 Health 응답의 세부 정상 판정 기준
- 그룹 내 Health URL과 애플리케이션의 개수 및 연결 관계
- Health URL 접근 보안과 인증 방식
- CloudWatch Logs 로그 레벨 검색 방법, 스트림 선택·표시 방식
- 로그 보존 기간 및 서버 측 로그 전송 구성
- S3 일 단위 지표의 조회·캐시 세부 정책
- 로컬 제어 작업 기록의 파일 형식과 보존 정책
- JSON 설정 파일 손상 시 복구 정책
- 실제 AWS 테스트 시 비용과 안전 조치의 세부 절차

기존에 확정한 사항(예: 그룹 내 다중 리소스 허용, 그룹 간 중복 등록 금지, 그룹 시작 순차 처리, 기본 타임아웃)을 미결정으로 되돌리지 않는다. 새 미결정 사항이 발견되면 문서에 추가하고 임의로 정하지 않는다.

## 15. 개발 및 검증 원칙

- 기능은 요구사항 ID 단위로 구현하고, 해당 기능의 관련 요구사항과 미결정 항목을 먼저 확인한다.
- 관련된 구현 단계의 기능 및 테스트를 마친 뒤 다음 작업으로 진행한다.
- AWS 실제 제어 검증은 사용자가 해당 대상과 작업을 승인한 경우에만 수행한다. 승인 전에는 모의 응답·로컬 테스트로 검증한다.
- 인증, 권한, 조회 실패, 빈 목록, 상태 전이, 시간 초과 및 부분 실패를 가능한 범위에서 검증한다.
- 테스트에서 확인한 내용과 수행하지 못한 검증을 구분해 기록한다.
- 요구사항과 실제 동작이 다르면 임의로 판단하지 말고 관련 문서를 갱신하거나 사용자에게 알린다.
